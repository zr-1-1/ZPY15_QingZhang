## 结论

**当前代码不能顺利生成预期的六维碎片轨迹文件。** CSV 分支生成 `6×345` 轨道根数，但随后的可视化要求 `345×6`，会先触发断言；即使跳过可视化，递推赋值也因只接收三维位置而报错。步长索引还有独立缺陷，目前被 `t_step=1` 掩盖。

| 优先级 | 问题 | 当前影响 |
|---|---|---|
| 高 | `orbit6toRV` 的双输出被当作一个六维输出使用 | 首次递推赋值报错，无法到达保存语句 |
| 高 | 上游、可视化、递推的根数矩阵方向不统一 | CSV 路径在递推前中断；简单转置又会破坏递推取值 |
| 中 | 物理时间直接用作数组下标，且固定从 1 秒起算 | 非 1 秒步长出现错位、漏点、扩容或非法下标 |
| 中 | 只保存 `x_rv`，缺少时间、碎片标识和模型信息 | 后续导入依赖外部约定，难以检查文件是否适用 |
| 条件性 | 碎片数量写死、全局参数与工作目录依赖 | 数据规模或分节运行环境变化时可能失败或算错 |
| 资源风险 | 约 2981 万次逐点转换、约 1.33 GiB 状态数组 | 运行与保存成本较高，尚未做完整规模实测 |

## 1. 高：返回值接收错误，六维状态无法写入

位置：`src/Data_Extract.m:184、266–296`。

```matlab
x_rv(:,i,t+1) = orbit6toRV(E_t,mu)';
```

局部函数签名是 `function [r,v] = orbit6toRV(orbit_elements, mu)`，`r`、`v` 分别为 `3×1` 列向量。单输出调用只取得 `r`，转置后为 `1×3`；左侧要求 `6×1`，因此不是单纯的行列转置问题，还遗漏了速度。

在实际 CSV 第一个碎片、`t=1 s` 的小规模复现中，右侧尺寸为 `[1 3]`，赋值产生 `MATLAB:subsassigndimmismatch`。无需运行一天轨迹即可确认。

建议按双输出契约接收并纵向拼接：

```matlab
[r_t, v_t] = orbit6toRV(E_t, mu);
x_rv(:,i,k) = [r_t; v_t];
```

其中 `k` 应为采样序号，见第 3 节。项目另有返回 `N×6` 的 `orb_elements2rv`，它和本局部函数的输出契约不同，不能直接混用。

## 2. 高：根数矩阵方向不统一，输入来源也不能直接互换

位置：`src/Data_Extract.m:29–39、44–77、179–181、210`。

当前存在两种数据布局：

| 来源或使用位置 | `Debris_oe` 布局 |
|---|---|
| ATK 提取及 `data.mat` 中的轨道根数 | `345×6`，每行一个碎片 |
| CSV 转换（第 52、63 行） | `6×345`，每列一个碎片 |
| 可视化断言和缩放 | 要求 `N×6` |
| 本次递推 `Debris_oe(:,i)` | 要求 `6×N` |
| 后续另一段递推 `Debris_oe(i,:)` | 要求 `N×6` |

实际 CSV 有 345 行，本次转换得到 `Debris_oe=[6 345]`、`Debris_rv=[6 345]`，执行当前可视化断言失败。因此，即使 ATK 前置部分顺利完成，按当前顺序执行到 CSV 分支后也不能进入目标递推段。

**不能只取消第 65 行的转置注释。** 转置后可视化可接受，但目标段的 `Debris_oe(:,i)` 会变成跨碎片取同一种根数，前六次取值已经错误，到第七列还会越界。

此外，ATK 循环中的 `Debris_rv` 每次覆盖前一个碎片，只留下最后一个碎片的状态，未建立 `6×345` 初始状态矩阵。本次只读检查现有 `data.mat`，其中 `Debris_oe` 为 `[345 6]`，另存的 `Debris_rv` 仅为 `[6 1]`；第 44 行实际上只加载 `Debris_oe`。所以“只加载 `data.mat` 再运行目标节”不具备可靠的全部初始状态输入。

建议明确一种贯穿脚本的根数布局，并同步调整所有使用点。例如选择 `N×6`，则递推用 `E_0=Debris_oe(i,:)`；位置速度仍可维持 `6×N`，但须独立校验其数量、顺序和历元一致。不要依赖变量名相同就认为不同提取路径可直接替换。

## 3. 中：步长参数与时间索引不一致

位置：`src/Data_Extract.m:176–184`。

```matlab
x_rv = zeros(6, 345, Tr_0/t_step + 1);
for t = 1:t_step:Tr_0
    x_rv(:,i,t+1) = ...;
end
```

`t` 是秒数，`t+1` 只有在步长恰好为 1 秒时才等于正确的采样下标；循环起点固定为 1 秒也不符合一般步长。使用六维常量替代转换结果，隔离上一节返回值问题后，MATLAB 小算例结果如下：

| 总时长 | 步长 | 实际结果 |
|---:|---:|---|
| 4 s | 1 s | 分配 5 帧，写入下标 `[2 3 4 5]`，时间对应正确 |
| 4 s | 2 s | 原分配 3 帧，实际写入下标 `[2 4]`，扩容至 4 帧；对应传播时间为 1、3 秒，并非 2、4 秒 |
| 4 s | 0.5 s | 到 `t=1.5` 时下标为 2.5，产生 `MATLAB:badsubscript` |

若时长不能被步长整除，当前分配尺寸也可能不是整数。建议验证有限实数标量、`t_step>0`、`Tr_0>=0`，明确是否要求整除；要求整除时先用浮点容差检验商，再取整构造整数采样数量。

对于已验证可整除的参数，核心结构可采用：

```matlab
nSteps = round(Tr_0/t_step);
time_s = (0:nSteps)*t_step;
for k = 2:numel(time_s)
    E_t = OE_scl_ptb(E_0, time_s(k));
    [r_t, v_t] = orbit6toRV(E_t, mu);
    x_rv(:,i,k) = [r_t; v_t];
end
```

以上是报告中的建议片段，未替换源码。对当前 `t_step=1`，初始帧对应 0 秒、末帧对应 86400 秒，共 86401 帧，这一时间覆盖本身没有少一步的问题。

## 4. 中：保存文件缺少可独立解释的信息

位置：`src/Data_Extract.m:187–190`。

当前 `save(...,'x_rv')` 只保存数值数组。从文件本身无法确认第三维每帧对应哪个 UTC 时刻、第二维对应哪个碎片、使用了哪个传播模型及常量。当前 CSV 的 345 个碎片具有同一历元 `2030-11-14 08:00:00 UTC`，仿真终点为次日同一时刻；其 `StepSize=60`，而当前脚本另选 1 秒采样。改变输出采样步长并非错误，但应将实际步长保存。

建议随数组保存：

- `time_s`、带 UTC 时区的初始历元、`t_step`、`Tr_0`。
- CSV 原顺序对应的 `DebrisID`、`Name`，以及初始状态或可追溯的数据来源。
- 状态分量顺序 `[x,y,z,vx,vy,vz]`、m/m/s 单位和实际采用的参考系说明。
- 传播方法名称、`mu`、`R_E`、`J_2`，必要时包括脚本版本。

导入时校验 `size(x_rv,3)==numel(time_s)`、碎片标识数等于第二维、状态为有限实数。第 190 行紧接保存后全量加载同一变量没有计算必要；它可以作为单独的导入示例，若用于验收则应增加上述检查。

## 5. 传播模型适用性：算法调用思路成立，精度仍未验收

位置：`src/Data_Extract.m:62、181–184`、`src/OE_scl_ptb.m:10–20`。

`OE_scl_ptb(E_0,t)` 使用初始根数计算角速率，再乘以距初始历元的时间。因此每个采样点都从同一 `E_0` 推到绝对偏移 `t`，符合当前函数定义，无须把上一时刻根数再传入并乘以累计时间。

代码中的 `a,e,i` 保持不变，只更新三个角度，属于该函数注释声明的 J2 平均摄动近似。CSV 状态通过 `rv2orb_elements` 直接转换，代码中没有另外进行平均根数转换或短周期修正。由此不能把所得轨迹认定为经过完整含摄动力学验证的 ATK 逐秒轨迹。

CSV 还记录了 `MaxDegree=20`、`MaxOrder=20`、`UseDrag=1` 等配置，而本传播路径没有读取或使用这些配置。这是模型实现范围不同的证据；仅凭这些字段不进一步断言 ATK 实际启用了哪些力项，也不据此给出未经测量的位置误差。

建议根据最终用途决定验收方式：若用于粗筛，先明确允许误差；若用于近距离交会或最终轨道验收，应与参考传播在相同历元、参考系和力模型条件下比较整个 24 小时的位置与速度。减小输出步长只会加密采样，不能补足模型未包含的项。

## 6. 条件性风险与资源开销

### 固定数量及运行环境

第 178、180 行固定 345，与当前 CSV 数量一致，因此当前没有数量不匹配；筛选或扩充数据后可能在初值赋值处报错。应从已校验输入取得碎片数，而不是只改循环上限。

`projectRoot=pwd` 依赖当前目录恰好为仓库根目录；在 `src` 下运行可能查找错误的 `data` 路径。分节运行还依赖全局常量已正确初始化。`Data_Extract_vsl.m:16` 仍将全局 `R_E` 设为 `6378.137`，本脚本则使用米制 `6378137`；若会话被前者改写而未重新初始化，`OE_scl_ptb` 中半径平方项将缩小为正确值的百万分之一。完整执行本脚本的初始化可避免这一特定会话风险。

### 内存、计算和文件格式

当前 `double` 数组的理论数据大小为：

```text
6 × 345 × 86401 × 8 = 1,430,800,560 bytes ≈ 1.33254 GiB
345 × 86400 = 29,808,000 次传播及状态转换
```

实际进程峰值还包含临时变量、绘图、保存等开销；磁盘压缩后体积不等于上述内存大小。本次未分配完整数组或实测总耗时。

**当前数组未超过 MAT v7 的单变量容量限制，不能把缺少 `-v7.3` 判为必然保存失败。** 如果后续扩大规模，或需要按块写入和读取，应考虑 Version 7.3 与 `matfile`。格式容量及部分读写能力参见 [MathWorks：MAT File Versions](https://www.mathworks.com/help/matlab/import_export/mat-file-versions.html) 和 [Large MAT Files](https://www.mathworks.com/help/matlab/large-mat-files.html)。

计算方面可在确认正确性后预计算每个碎片的不变参数，并按碎片或时间块生成和保存。当前仅在全部计算结束后保存，中途失败不会留下本轮完整结果；后续手动加载时也应防止把旧的同名文件当成本轮输出。
